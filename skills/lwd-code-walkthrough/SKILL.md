# LWD 代码串讲

目标: 让听的人理解每一处改动的设计意图, 能据此判断改得对不对. 默认听的人熟悉 LWD 业务, 但不一定熟悉 vLLM 原生代码.

## 节奏

- 顺着 diff 一处一处讲, 一次只讲一处; 讲完说明下一处是什么, 等用户说继续.
- 只读讲这一处需要的上下文. 不要开讲前先全仓调研影响面; 影响面在讲到相关的那一处时再展开.
- 不跑测试、不跑也不写演示脚本. 例子从代码推导, 标明"示意"或"推断, 没跑过".
- 串讲中不改代码、不 commit. 发现要改的地方列为问题, 问用户要不要改.

## 每一处讲之前先想清楚

1. **改前为什么这样**: 旧代码在解决什么, 或者在抵消什么 (例: 强制 `is_first_rank` 返回 True, 是在抵消借来的 PP 组).
2. **改后为什么这样**: 新设计下这段代码的理由.
3. **这段代码还该不该存在**: 是不是旧机制的残留. 和三处对照:
   - main 或配套 PR 里同一件事的做法 (例: mm 强制 `pipeline_parallel_size = 1`, main 不设 pp、只对 pp>1 报错, 说明 mm 那行是残留);
   - 原生 vLLM 代码 (改回原生的, 用 diff 确认是否逐字一致);
   - 全仓 grep 旧名字, 确认没有残留引用.

   自己做过的机械改动 (改常量、改条件) 尤其要问: 该删还是该改.
4. **需求出处**: 这处改动对应哪条需求. 用户给过会议记录、issue、RFC 的, 引用原话并带时间戳或链接 (例: `[637s–665s] "把两段 PP 那个东西给它摘出来"`).
5. **原生 vLLM 怎么做**: 改动绕开或恢复的原生机制是什么 (例: 均匀 rank 网格、PP 首/尾段分工、async 调度下尾段广播 token). 用一两句加代码位置讲清楚.
6. **配套仓**: vllm-ascend 或 vllm 里与这处成对的改动.
7. **问题**: 按严重度排, 标证据等级 (实证/推断/假设), 并区分是这次引入的还是原本就有的.

## 每一处的讲解结构

1. 标题: `第 N 处: <文件> (<函数>)`, 后接对应的需求出处.
2. **结论**: 按上面 1–3 各一两句, 放在最前面.
3. **例子**: 用一个具体布局. 需求出处里有例子的就用那个 (例: 会议里的边 0、1 + 云 2–5). 用表格逐 rank 或逐进程列出改前、改后的取值.
4. **原生对照**: 需要时贴原生代码片段和位置.
5. **diff 分块**: 每块给改前/改后的精简片段和 `path:line`, 一两句说明这块在整个机制里的角色.
6. **特殊场景**: 只在这一处的行为随场景变化时展开 (多 DP、多边一云、一边多云、`edge_share`/`cloud_share`/`lwd_cluster`), 用表格列各进程的取值; 不变就一句话带过.
7. **这一处的问题**: 没有就写"没有发现新问题".
8. **下一处**: 一句话说明下一处讲什么.

## 回答追问

- 用户问"是什么意思""为什么", 默认是在问设计意图. 第一句给结论, 再给依据; 不要用字段含义、调用方列表、影响面表格代替结论.
- 用户问"简单来说是不是 X": 先答"对""不对"或"对一半", 再用一两句说清差别.
- 用户的理解对一半时, 指明哪一半对, 用具体例子纠正另一半.
- 用户连续追问同一点, 说明上一轮没答到点上. 回到"每一处讲之前先想清楚"的 1–3 重新想, 不要往外补更多细节.
- 追问揭示了该改的地方 (残留、死代码、过时注释): 提出改法, 问用户, 不要直接改.

## 证据

- "和原生逐字一致""没有残留""没有调用方"这类断言, 必须在当轮用 diff 或 grep 确认过.
- 读代码推出来但没运行过的结论, 标"推断"; 没分析过的, 标"假设".

## 格式

- 中文讲解; 代码、标识符、日志原文保持英文.
- 文件位置写成 `path:line`, 便于点击跳转.
- 逐 rank、逐进程、改前改后的对比用表格.
- 数字用 k/m, 不用"万".
- 用户认可的讲解 (例如一个关键例子), 问用户要不要落到对应模块的 docstring 里 (英文、精简、带一个例子).
- 讲解时把一个函数拆成了几步的, 代码里也应有对应的编号注释 `# N. 做什么: 为什么`; 没有的, 列为问题提出来.
